## 一、交卷是怎么走通的（关键补充）

前面几轮一直以为卡在"缺 `question_id`"，最后是靠**浏览器路径**打通的。三步：

1. **进测验章节**（浏览器点开「课后测验」）→ 页面链：
   `api/work`(302) → `workHandle/handle`(302) → **`doHomeWorkNew`(200, 177KB)**
   —— 只有这条链上的 `doHomeWorkNew` 才**带题号**（`id="question403175391"` /
   `input[name="answer403175391"]`）；
2. **取可读题干**：页面 DOM 里的题干是**字体加密**的（`font-cxsecret`，形如「摓会摔摒摐摊」），
   所以题干必须从**明文题接口**取；两侧**顺序一致**，按索引合并即可；
3. **交卷**：填 `input[name^="answer"]` 的值后提交，接口是
   `POST /mooc-ans/work/addStudentWorkNewWeb?_classId=…&courseid=…&token=…`
   → **200**，服务端返回成绩。

**顺带发现两件事**：

- **选项顺序是打乱的**：同一道题，明文题接口的选项顺序与页面**不同**
  （例：明文 `A 个体心理评价标准 / B 社会文化标准 / C 医学标准 / D 统计学标准`，
  页面 `A 社会文化标准 / B 个体心理评价标准 / C 统计学标准 / D 医学标准`）。
  所以**答案必须按页面顺序给**，不能直接套明文接口的字母；
- **提交后题干就变可读了**：交卷前 DOM 是加密字符，交卷后同一页面能直接读到
  「依据心理特征偏离常模的程度为标准，判断人的心理健康状态，属于( )」——
  说明加密是**作答期**的防作弊措施。

## 二、视频心跳：仍 403

`ktoken` 修复对它**没有帮助**（心跳 URL 里本就不含 `ktoken`）。

### 抓不到对照样本的三个层层递进的原因

**第一层（已排除）**：以为是"章节未解锁"。手工拼章节页地址时页面显示
**「温馨提示 / enc校验失败」** —— 那是 **`enc` 与章节不匹配**（`enter_course` 拿到的 enc
只对默认章节有效），不是解锁问题。

**第二层（已确认）**：改用**浏览器点章节**（页面自己带正确的 enc）后，`3.3.1 焦虑类型`
的标题变成 **「学生学习页面」**、iframe **7 个** —— **章节确实已解锁**。
说明上一轮交卷的章节测验**解锁了后续内容**。

**第三层（当前卡点）**：页面顶部显示 **「任务点已完成」**，右侧目录里 3.3.x / 3.4.x / 3.5.x
**大多带绿勾** —— 也就是说这个视频**学习通侧早已完成**，而**已完成的视频不产生心跳上报**。

### 由此暴露的真问题：本地完成状态与实际脱节

本地 `task_points.status` 把 3.3.1 记成 `queued`，而学习通侧是"已完成"。
后果是刷课编排会挑中这些"本地以为没做、实际早做完"的任务点反复去撞 ——
既发无效请求，也拿不到心跳。**需要补一个"从学习通同步任务点完成状态"的能力**，
这比继续找心跳参数更实际。

### 剩下的路

1. ~~补状态同步~~ → **已完成**（`CourseService.sync_progress`，实测一次纠正 71 个脱节点）；
2. ~~找一个真正未完成的章节做对照样本~~ → **已排除**：同步之后查了一遍，
   这个账号的**视频任务点全部已完成**（仍待处理的 14 个**全是 quiz**）——
   也就是说**在当前账号上根本产生不了心跳场景**，不是参数问题，是没有需求；
3. 要验心跳，只能**换一个有未完成视频的账号或课程**。

### 所以心跳这条链路的最终状态

**无法验证 ≠ 实现有问题**。已有的证据是：

- 心跳请求的**每个参数**都与参考实现逐字对齐过（签名、`dtoken`、`otherInfo`、`clipTime` 等）；
- 服务端拒绝已完成的视频上报**本身是合理行为**；
- 而这个账号**没有未完成的视频**，所以从未有过"该发且应该成功"的心跳请求。

换句话说：这条链路的问题描述应该是「**缺一个可验证的场景**」，而不是「403 挡住了功能」。
在此之前它一直被我当成"待修的缺陷"，那是不准确的。

### 还剩下什么

真实播放器与我们的差别只剩一处：**它真的在播**（`video.play()` 之后按进度上报），
而我们只是"按参数拼出同一个请求"。也就是说 403 的成因很可能不在**请求长什么样**，
而在**服务端对"这个用户此刻是否真在看"的判断** —— 这类判断通常靠一个我们还没发现的
前置调用或某个一次性令牌。

但要继续追下去，前提是**先让播放器真的播起来**。而这一步在这一轮被另一个东西挡住了：

    控制台报错：Robot initialization failed: Error: CxRobotSdkJs is not loaded

新版播放器要加载**人脸识别 SDK**（`CxRobotSdkJs`）才创建 `video` 元素 —— headless 环境下
这个 SDK 拿不到，所以**页面上连 `video` 元素都不存在**（实测：7 个 iframe、`video` 计数为 0），
自然也不会产生任何心跳。这不是我们的实现问题，是**验证手段**（headless 浏览器）被反爬措施挡住了。

### 用真实样本反算签名 —— 算法验证通过（2026-10 再补）

拿到真实心跳后做了一件此前做不到的事：**用它的已知输入反算 `enc`**。

### 实验 A：真实 URL 的"可变性"测试（2026-10 再补）

拿到一条能 200 的真实 URL 后，做了组对照实验（都用同一个 httpx 客户端、账号 1 的 cookie）：

| 实验 | 改动 | 结果 |
| --- | --- | --- |
| A0 | 原样重放 | **200** |
| A1 | `playingTime` 改成 30（重算 `enc`） | **200** |
| A1 | `playingTime` 改成 60（重算 `enc`） | **200** |
| A2 | 只换 `_t`（`enc` 不动） | **200** |
| A3 | 把 `enc` 改成全 0 | **403** |

**读出来的三件事**：

1. **服务端确实校验 `enc`**（A3 是反证：签名一坏就 403）；
2. **播放进度可以随便改**（A1：30、60 都能过）—— 心跳不是"只能上报真实看过的位置"；
3. `_t` 不需要精确（A2）。

也就是说：**一条有效的心跳 URL，其参数是可以动态改的**。那么同样的形状、同样的签名算法，
在我这边却稳定 403，差异就只可能在**那些由卡片/服务端签发的绑定值**上 —— 而它们我都原样转发了。

### 顺带排掉一个格式嫌疑

我的 payload 里 `attDuration` 存成了 `'600.0'`（带小数点），真实样本是 `'441'`（整数）。
改用整数重发 —— **仍然 403**。格式不是原因。

### 依赖清理

上一轮为了验证 TLS 假说装过 `curl_cffi`；既然"httpx 重放真实 URL 得到 200"已经证伪了那条假设，
这个依赖**没有任何存在理由**，已 `uv remove` 掉。（浏览器相关能力后来整体改为 **orca-cli** 驱动，
项目里已不再自带 `playwright` —— 见 `docs/PROTOCOL_COVERAGE.md` 的「对账方式」。）

### 收敛后的状态

心跳的**可判定部分**全部验完了：签名（对）、传输（对）、cookie（对）、参数形状（对）、
参数可变性（进度可改）、格式（无关）。剩下唯一没验的，是**"服务端凭什么认为这个请求来自一次真实播放"** ——
而那需要一条**由我这边播放产生的、被接受的**心跳做对照。这一步无法在无头环境里完成
（人脸 SDK 不初始化 → 页面不创建 `video` 元素）。
### 从播放器 JS 里读到 403 的**语义**（2026-10 再补）

把混淆的字符串表解出来（1277 项）之后，在心跳发送函数 `_0x296e6d` 里看到了它对响应的处理：

```javascript
videojs.xhr({ uri: url, headers: { 'Content-Type': 'application/json' } },
  function (_, res) {
    if (res.status == 0xc8) { ... }              // 200
    if (res.status == 0x193) {                   // 0x193 = 403
        var m = body.match(/\[restTime:(\d+)\]/);
        var minutes = m ? Math.floor(parseInt(m[1]) / 60) : 5;
        tip('本次学习时长已达上限，请休息 ' + minutes + ' 分钟' +
            '后重新进入学习，继续观看将不记录视频观看时长');
    }
  });
```

**这改变了对 403 的定性：它不是"请求不合法"，而是服务端用它表达业务拒绝。**
"本次学习时长已达上限"就是其中一种（带 `[restTime:N]`）。

于是很多此前费解的现象一下子说得通了：

- 为什么**参数逐个对齐也照样 403** —— 因为参数本来就没问题；
- 为什么文档前半会观察到"**有时成功、有时 403**" —— 时长累积到上限前后本来就该不一样；
- 为什么 JS 要在前端专门做一个 403 分支来提示"休息" —— 它是**预期内的业务状态**。

### 我这个 403 不是"时长上限"

把完整响应体打出来（2342 字符）看过：是通用错误页，**没有 `[restTime:N]`**，只有一个 `code=6`。
所以它是**另一种业务拒绝**，与"休息"无关。

字符串表里与心跳失败相关的提示语只有这几条，没有 `code=6` 的对照：

    同步学习数据失败，错误码：
    服务繁忙，不能保证您能否正常完成任务，请您稍后继续...
    您的网络不稳定，请您稍后继续...

### 另外两处顺带确认的细节

- 心跳请求**确实带 `Content-Type: application/json`**（GET 也带）—— 与我们此前从真实样本观察到的
  一致，我们的实现也已经带上；
- 发送函数开头有个提前返回：`if (top.hasJobLimit === true && isUnFinishJob()) return;` ——
  即"有未完成作业时不发心跳"。那是**不发**，不是 403。

### 现在的判断

心跳 403 的**可判定部分已经全部验完**（签名、传输、cookie、参数形状、可变性、格式），
剩下的差异属于**服务端业务判定**（`code=6` 的具体含义未在客户端代码里出现）。
要把它变成可复现、可修复的结论，只能拿到**一条由真人播放产生的、被接受的**心跳做对照 ——
它必然 200，与我的逐字段一比，剩下的差异无处可藏。
### 逐字段替换实验：定位到 `otherInfo`（2026-10 再补）

拿到一条能 200 的真实 URL 之后，做了一件此前做不到的事：**把它当基线，逐字段换成我的值**。

**先做交叉实验**（排除账号与 cookie）：

| 组合 | 结果 |
| --- | --- |
| 真实 URL + 账号 1 的 cookie | **200** |
| 真实 URL + **账号 2 的 cookie** | **200** |

**账号 2 本身没有任何问题** —— 服务端甚至不校验 cookie 与 URL 里 userid 的一致性。

**再逐字段替换**（都在真实 URL 上改，改了签名就重算）：

| 改动 | 结果 |
| --- | --- |
| A0 基线（原样） | **200** |
| A1 换 `userid`（重算 enc） | 403 |
| A2 换 `clazzId`（重算 enc） | 403 |
| A3 换 `courseId` | **200**（无关） |
| A4 换 `playingTime`（重算 enc） | **200**（无关） |
| **B1 只换 `otherInfo`** | **403** ← 就是它 |
| B3 只换路径里的 cpi/dtoken | 403 |

**`otherInfo` 是唯一的决定性字段。** 继续在它内部二分（它的结构形如
`nodeId_x-cpi_x-rt_x-ds_x-ff_x-be_x-vt_x-v_x-enc_x`）：

| 改动 | 结果 |
| --- | --- |
| D0 纯真实 | **200** |
| D1 只换 `enc_` 那一段 | 403 |
| D2 只换 `nodeId` | 403 |
| D3 只换 `cpi` | 403 |
| D4 只换 `ff` | 403 |

**读出来的结论**：`otherInfo` 不是"一堆独立字段"，而是一个**整体签发的自洽串** ——
**改动其中任何一段都会让它失效**。它由卡片接口签发，我们只能原样转发（已经在做）。

### 顺带纠正一个猜测

先前怀疑 `ff_d` / `ff_1` 是关键差异，实测**不成立**：同一账号不同章节的 `ff` 取值本就不同
（「课程概述」是 `ff_1`，其余是 `ff_d`），而且**两者心跳都 403**。
C3 实验里"把真实的 `ff_d` 改成 `ff_1` 也变 403"，原因只是**改动破坏了 `enc_` 的自洽性**，
与 `ff` 本身无关。

### 收敛到最后的差异

到这里，两条 URL 的差别只剩**那些由服务端成套签发的值**：

| 字段 | 真实 URL | 我的 URL | 谁签发 |
| --- | --- | --- | --- |
| `otherInfo`（整串） | nodeId_1214035150… | nodeId_1190504501… | **卡片接口** |
| `objectId` | 986cd910… | 21cb255b… | 卡片接口 |
| `jobid` | 164905573148985 | 1706077910363539 | 卡片接口 |
| `dtoken` | 9eb1bcae… | 8d7798fe… | `/ananas/status` |

**它们全都由服务端签发、我们全都原样转发**。也就是说：在我的实现这一侧，
**已经没有可以再改的东西了** —— 请求的每一个字节都来自服务端的真实响应。

### 这一步的意义

问题从"不知道哪里错了"变成了一个**边界清楚的陈述**：

> 用账号 2 自己卡片签发的 `otherInfo`/`objectId`/`jobid`/`dtoken` 组装的心跳，
> 服务端返回 403（`code=6`）；而用账号 1 卡片签发的同一组值组装的，服务端返回 200。
> 两者的**请求形状、签名算法、传输方式、cookie 完全一致**。

剩下的差异只可能在**服务端对这组签发值的判定**上。要再往前一步，需要一条
**由账号 2 真实播放产生的、被接受的**心跳 —— 那会把"服务端到底在判什么"直接摊开。
## 五、**打通了** —— 根因是"打开播放器页"这一步（2026-10 定论）

### 决定性实验

把两个条件放在一起对比（同一账号、同一 objectId、同一参数、同一签名）：

| 是否先打开播放器页 `/ananas/modules/video/index.html?v=…` | `status` 签发的 dtoken | 心跳结果 |
| --- | --- | --- |
| **否** | `8d7798fe5f873cb76be6926f2e6cfd47` | **403** |
| **是** | `9eb1bcaeede460b220c37412950e77bc` | **200** ✅ |

`9eb1bcae…` 正是 `.browser-check/hb-real.json` 里那条真实心跳用的 dtoken —— **对上了**。

**根因**：`/ananas/status` 会签两种 dtoken。只有在**播放器页被访问过之后**签发的那一个，
才被服务端认作"属于一次播放会话"。拿另一个去心跳，参数再对也是 403，
而且 403 给的是一张通用错误页（`code=6`），不提示任何原因。

这解释了我们此前所有的困惑：

- 参数/签名/cookie/传输**全都对**却一直 403 —— 因为缺的是这一步**会话前置**；
- 文档前半观察到的"有时成功、有时 403" —— 那次成功的请求恰好落在播放会话里；
- 播放器 JS 里的 403 分支只在提示"学习时长上限" —— 那颗 `code=6` 是**另一种**业务拒绝，
  前端根本没做它的分支。

### 修复

`VideoApi.fetch_info()` 现在**先打开播放器页**再取元信息（`open_player()`），
并在测试里钉住这条顺序：mock 少了播放器页会让测试直接报"未 mock 的请求"——
那正是修复生效的证据。

### 一个仍需真人配合的边界

在**从未被播放过**的视频上，打开播放器页后 dtoken **不会变**，心跳仍 403
（账号 2 的「诗话青春——绪论」，30 秒，实测如此）；而在**曾被真实播放过**的视频上，
打开播放器页 dtoken 立刻变成可用于心跳的那个（账号 1，实测 200）。

也就是说：`dtoken` 的"资格"要么由一次真实播放激活，要么在激活后长期有效。
**我们这一侧能做的已经全部做到了** —— 剩下的只有"首次播放"这一次人工动作。
`code=6` 很可能就是这层"尚未激活"的表达。

> ⚠️ **上面这条结论已被 §六 推翻**（2026-10-15）。`open_player` 本身没错，但它不是 403 的解药；
> "未激活必 403"也不成立 —— 之前所有样本都带着同一个 `otherInfo` 缺陷。

## 六、**真根因（2026-10-15 定论）**：`otherInfo` 带了页面的 `&courseId` 尾巴

同一条 URL、同一个 `dtoken`、同一账号，只交叉替换 cookie 与参数：

| 组合 | 结果 |
| --- | --- |
| V1 用户 cookie + 用户参数 | **200** |
| V2 **工具 cookie** + 用户参数 | **200** ✅ |
| V3 用户 cookie + **工具 URL** | **403** |
| V4 工具 cookie + 工具 URL | **403** |

⇒ 工具的**会话完全合格**（V2 = 200）；差别在**参数**。逐参数对比后收敛到一处：

| 参数 | 真实心跳（浏览器实际发出） | 工具（修复前） |
| --- | --- | --- |
| `otherInfo` | `nodeId_…-enc_<hash>` —— **到此为止** | 尾部多挂 `&courseId=<id>` ❌ |

只把这一处截断、其余一个字符不动 → **t=0 / 200 / 285 三个进度点全部 200**。

**为什么会多出来**：页面 JSON 里的 `otherInfo` 确实是 `…-enc_<hash>&courseId=<id>`（§四 里
"照抄页面形状"的实验因此失败 —— 抄的是页面形态，不是浏览器真正发出的形态）。播放器 JS 在发心跳时
把 `courseId` 拆成**独立查询参数**，`otherInfo` 只到 `-enc_<hash>`。

**修复（三处收口，提交 `00d90ca`）**：

- `client/model/card.py`：`other_info` 加 `field_validator` 截断 —— **唯一收口**，HTML 与 JSON 两条解析路径全覆盖；
- `client/parser/card.py::extract_other_info`：在提取处截（根因位置）；
- `client/api/video.py::build_heartbeat_params`：构造处兜底 —— **库里早先扫下的 payload 带着尾巴，无需重扫即可恢复**。

测试钉住：`tests/client/test_parser_card.py::test_other_info_is_preserved_verbatim` 现在断言
`"&courseId=" not in other_info` 且 `"&" not in other_info`。

**顺带纠正的历史误判**：

- 「必须先打开播放器页才有 200」—— `open_player` 保留（它让 dtoken 可用），但不是 403 的解药；
- 「未激活的视频必 403」—— **不成立**，样本全带着同一个缺陷；
- 「账号被视频反作弊标记」「必须真人先播一次」—— **均不成立**，同源缺陷的投影。

## 七、测验链路：换票 403 定论 + 提交目标 + 人工验证码（2026-10-16）

### 7.1 换票 `api/work` 的 403：**`ktoken` 是旧的**（定论）

同一条 URL、同一会话，**只换 `ktoken`** 做 A/B：

| `ktoken` | 结果 |
| --- | --- |
| 浏览器现用（`ffc558eb…`） | **200** ✅（302 到 `doHomeWorkNew`） |
| 库里存的（`0e637043…`，扫描那一刻的） | **403** ❌ |

⇒ 与 TLS、Referer、XHR 头、会话上下文**全都无关**。修正方向早就在代码里
（`CourseService.refresh_quiz_tokens()` 会拿卡片的 `defaults.ktoken`）——
真跑一次 1436 已实测**越过换票**（`_run_quiz` 的栈从 403 变成提交阶段）。

**这条也解释了历史observations**：所谓「`mooc-ans/*` 两个接口都被拒、疑似需要不同会话上下文」
是**旧票据**的投影，不是会话问题。

### 7.2 交卷：提交目标必须是**页面表单自己的 action**

题目页的 `form1` 带的 action 与"自拼查询串"完全不是一套：

| 浏览器（action 原文） | 工具（修复前自拼） |
| --- | --- |
| `_classId` / `courseid` / `workid` / `testmooc2` | `classId` / `courseId` / `workId` / `mooc2` |
| **`token=<隐藏域 enc_work 的值>`** | 无 |
| **`totalQuestionNum`** | 无（只在 body） |
| 无 | `api` / `enc` / `pos` / `rd` / `wid` / `_edt` / `ua` / `value` / `version` / `saveStatus` / `submit` / `isphone` |

**字段集一模一样（29 / 29，无缺无多）也照样被拒** —— 键名与取值必须照 action 原样，
再加 `version=1`（页面走 `version(document.form1.action)`）。
修复：`client/parser/quiz.py::extract_form_action()` + `QuizApi.submit(form_action=…)`。

### 7.3 交卷前的**校验码预检**（`workTimesEnc` 的来源）

题目页 `form1submit()` → `confirmSubmitWork()` 会先 `$.ajax` 到
`/mooc-ans/work/verify/code`，**成功时把响应的 `enc` 写进 `workTimesEnc`** 再真正提交：

```
GET /mooc-ans/work/verify/code?courseId=…&classId=…&cpi=…&workId=…&answerId=…&inputCode=
→ 200 {"enc":"e0bfc5fb93983650f5a53535ee72ba24","status":true}
```

⇒ 缺这一步、body 里 `workTimesEnc` 为空 —— 服务端一律回**「作业提交失败！」**。
注册表里原来的 `/verifyCode/stuWork` 是**验证码图片**入口（`workVerifyCode()` 用它设 `<img>.src`），
不是这个 JSON 接口；已拆成两个端点（`quiz_verify_code` / `quiz_verify_image`）。

### 7.4 仍缺的一环：**人工验证码**（机器过不去）

答卷被服务端置入「要求人工验证码」态后，同一接口会回：

```json
{"msg":"验证码不正确，请重新输入","status":false}
```

- **同账号、同参数、不同会话**结果会在这两句之间**摆动**（工具会话时而 `status:true`、
  浏览器会话时而「验证码不正确」）—— 所以**不能靠字符串匹配判断**，必须**主动探针**：
  提交失败后用空码再探一次 verify，它说验证码不对就把原因归位（`client/api/quiz.py::submit`）。
- **OCR 实测不可用**（2026-10-16）：`ddddocr` 默认模型 / 中文 `beta` 模型 / 二值化+中值去噪+3×放大，
  三种都输出乱码（长度 3–6 不等），说明该校验证码不是常规字符型。
- 落地方式 = **验证码接力**：`QuizApi.fetch_verify_captcha()` 取图 →
  `StudyService._save_quiz_captcha()` 落 `data/captcha/quiz-<workid>-<ts>.jpg` →
  抛 `HumanRequired`（消息含路径）→ 人工读出四位码后
  `StudyService.run_quiz(account_id, point_id, input_code=…)` 完成交卷。

### 7.5 顺带纠正的历史误判

- 「测验可以直接拼 `doHomeWorkNew`」—— **不行**，3004；必须走换票（但换票只差一个**新鲜 `ktoken`**）；
- 「提交失败是答案格式/缺字段」—— 报文形状已与浏览器**逐字节一致**仍被拒，真因是**验证码态**；
- 「扫描时存的票据可以直接用」—— `enc` 分钟级轮换、`ktoken` 更短命，**执行前必须就地刷新**。

## 八、参考实现对照与本轮加固（2026-11-07）

对照两个公开实现（只取逻辑，不复制代码）：

| 逻辑 | Samueli924/chaoxing | RainySY/autoflush | 本轮落地 |
| --- | --- | --- | --- |
| 请求节流 | `RateLimiter` 按调用间隔 sleep，视频上报再加 0~2s 抖动 | 无 | 传输层已有**账号级** `request_min_interval`；代理重定向改走同账号出口（见下） |
| 任务点扫描 | `knowledge/cards?num=0..6` 逐张累加，空卡即止 | `num` 递增直到解析不到 | 已有 0..9 逐张扫描，且章内序号计入 `num` |
| 换票失败 | `fetch_response_with_retry` 最多 3 次，1s 间隔 | 不涉及 | 新增 `_open_quiz_page`：403/3004 后**重新扫卡刷新票据**再换一次，不重放旧票据 |
| 提交失败 | 单轮模式只提交一次；重做模式靠成绩反馈再答 | 不涉及 | 保留“POST 不自动重试”；交卷前按页面 action + `verify/code` 预检，失败只探针归因 |
| 答案形状 | 判断题 `true/false`、多选排序去重 | 不涉及 | 已有 `normalize_answer` + `sanitize_answers_by_type` + 题型对齐 |
| 视频心跳 | 每 30~90s 视频时间上报一次，结束补 `isdrag=4`；403 刷新 status/重登 | 每 60s 上报，进度 +5s×倍速，结束 `status=4` | 保持本项目实测口径（真实节奏 12~20s、`isdrag=3`、以回执判定），不引入倍速多报 |
| 未答题目 | 随机答案/低覆盖不提交 | 不涉及 | **缺一题就不交卷**（`quiz_require_full_answers`）；不再留空提交部分答案 |

本轮改动的三处：

1. `client/api/quiz.py::_verify_code`：按 XHR 形状带 `X-Requested-With`/`Referer`，
   并兼容题目页的 `courseid` / `classid` / `workid` / `answerId` 别名；
